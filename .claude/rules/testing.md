# 単体テスト / 結合テスト / E2E の切り分けと骨抜き禁止

## TypeScript

### 種別と実行コマンド

| 種別    | ツール        | 配置場所                 | 実行コマンド                     | 主な検証対象                             |
| ----- | ---------- | -------------------- | -------------------------- | ---------------------------------- |
| 単体テスト | Vitest     | `tests/unit/`        | `npm run test:unit`        | 純粋ロジック、境界値、異常系                     |
| 結合テスト | Vitest     | `tests/integration/` | `npm run test:integration` | API Route、Server Action、DBを含む制御フロー |
| E2E   | Playwright | `tests/e2e/`         | `npm run test:e2e`         | 主要ユーザーフロー、認証・認可、画面・APIをまたぐ状態遷移     |

`npm run test` は単体テストと結合テストをまとめて実行する。

* `tests/unit/` と `tests/integration/` は、対象となる `src/` 配下の構造を再現する。
* E2Eは、必要なシードデータを投入し、対象アプリケーションが起動した状態で実行する。
* テスト種別ごとの責務を混在させない。

### 単体テストとE2Eの切り分け

#### E2Eで検証する

以下はE2Eで検証する。

* 主要ユーザーフローが開始から完了まで正常に動作すること
* 認証・認可が正しく機能すること

  * 他ユーザーのデータへアクセスできないこと
  * 権限によって表示・操作可能範囲が変化すること
* 複数画面や複数APIをまたぐ操作
* ローディング、成功、エラーなどの状態遷移
* 実際のアプリケーション内部APIとの通信を含むフロー

認証・認可に関する項目は、認証を導入している場合に適用する。

E2Eでは、アプリケーション内部のAPIレスポンスをモックしない。
ただし外部サービス（LLM、Web検索、株価・財務API）は、
実行時間と課金、結果の不安定さを避けるためスタブしてよい。

#### 単体テストで検証する

以下は単体テストで検証する。

* 純粋な計算処理
* データ整形
* バリデーション
* 外部I/Oを含まないロジック
* 境界値
* 異常系
* 条件分岐
* E2Eでは網羅しにくい細かなロジック

単体テストでは、DB・外部API・ファイルI/Oなどの外部依存を直接利用しない。

#### 結合テストで検証する

以下は結合テストで検証する。

* API Routeの挙動
* Server Actionの挙動
* DBアクセスを含む制御フロー
* 複数モジュールを組み合わせた処理
* E2Eにすると過剰なセットアップが必要になる処理

E2Eで内部実装を再現するためにモックが必要になる場合は、E2Eではなく結合テストとして検証する。

### E2Eのシードデータ

本節はデータベースを導入している場合に適用する。
データベースを持たない構成では、アプリを起動してE2Eを実行する。

```text
1. npm run dev
2. npm run test:e2e
```

* E2Eは、固定のシードデータを投入したテスト用データベースに対して実行する。
* 必要な場合は、以下をシードデータとして用意する。

  * ログイン可能なテストユーザー
  * 権限の異なるユーザー
  * 組織
  * プラン
  * テスト対象となる業務データ
* シード定義は1か所に集約する。

  * 例：`tests/e2e/seed.ts`
  * 例：`db/seed.sql`
* テストコード内にシードデータ由来のマジックナンバーを直接記述しない。

実行順序は以下とする。

1. `npm run db:seed`
2. `npm run dev`
3. `npm run test:e2e`

読み取り専用テストは、投入済みの共有シードデータを参照してよい。

データ変更を伴うテストは、各テスト専用のデータをfixtureで作成する。

共有シードデータを変更してはならない。並列実行時に他テストへ影響するため。

変更を伴うテストは、終了後に自分で作成したデータを削除する。

### 骨抜き禁止

テストを通すために、検証内容を弱めることを禁止する。

```ts
// NG: 実質的な検証になっていない
expect(result).toBeDefined();

// NG: 常に成功するモック
vi.mock("./api", () => ({
  fetchData: vi.fn().mockResolvedValue({}),
}));

// NG: テスト対象となる条件分岐を迂回している
if (!process.env.API_KEY) {
  return;
}

// OK: 期待値を明示し、境界値も検証する
expect(calcTax(1000)).toBe(100);
expect(calcTax(0)).toBe(0);
```

以下を禁止する。

* E2Eでアプリケーション内部のAPIレスポンスをモックする
* `.only` を残したままコミットする
* `.skip` を残したままコミットする
* 失敗しているテストを削除して通す
* assertionを削除して通す
* assertion条件を緩めて通す
* 実装に合わせて期待値を変更する
* テスト対象そのものをモックする
* 異常系を正常系として扱う
* テスト失敗時に早期returnして回避する

仕様変更により既存テストの期待値変更が必要な場合は、実装変更前に仕様変更であることを確認する。

## TDD

新規機能および不具合修正は、必ずREDから開始する。

手順は以下に固定する。

1. 失敗するテストを書く
2. テストを実行し、意図した理由で失敗することを確認する
3. 最小限の実装を行う
4. テストが成功することを確認する
5. テストが成功した状態を維持したままリファクタリングする

```text
RED
↓
GREEN
↓
REFACTOR
```

実装を先に行い、後からテストを追加することは禁止する。

### テストの独立性

* 各テストは、他テストの実行結果に依存してはならない
* 各テストは、他テストの実行順序に依存してはならない
* データ変更を伴うテストは、自分専用のデータを作成する
* 自分で作成したテストデータは、テスト終了後に削除する
* 他テストが作成したデータを参照しない

### 待機処理

固定時間の待機は禁止する。

以下は使用しない。

```ts
await page.waitForTimeout(3000);
```

Playwrightの自動待機または条件ベースの待機を利用する。

```ts
await expect(page.getByRole("heading", { name: "分析結果" })).toBeVisible();
```

必要に応じて `expect(...).toPass()` を利用する。

### セレクター

E2Eのセレクターは以下の優先順位で使用する。

1. `role`
2. `label`
3. `test-id`

CSSセレクター、DOM階層、class名への依存は禁止する。

例：

```ts
page.getByRole("button", { name: "分析する" });
page.getByLabel("投資テーマ");
page.getByTestId("company-card");
```
